"@rrweb/browser-client": minor
---

Export `createTransport` with its `Transport` and `TransportOptions` types, so callers that own a recording (such as the browser extension) can stream events with their own recording id and metadata. `stop(true)` now delivers events still buffered before sending `close-permanent`, and POSTs `close-permanent` when the socket is not open, so the end marker arrives even if the socket never connected. This also holds after the page was frozen, which closes the socket: `stop(true)` still POSTs what was buffered, then `close-permanent`. The close event is POSTed only after any POST already in flight settles, so it cannot overtake earlier events. `stop(false)` POSTs `close-temporary` when the socket is not open, instead of leaving it buffered. After the socket drops and reconnects, events go over the socket again instead of staying buffered, and the 5 second POST fallback runs again while the socket is closed. A server error still pauses the socket until the transport is stopped or disconnected. Calling `start()` twice closes the first transport's socket and POSTs any events it still buffered. `Transport.stop()` resolves to a `DeliveryResult`: `{ delivered: true }`, or `{ delivered: false, error, unsent }` when a POST failed, with the serialized events the server did not accept. It never rejects. The new `postEvents()` sends such events again. A POST that cannot reach the server now keeps its events for the next attempt, as a rejected POST already did, and a single large event whose own POST failed is kept in a POST-only queue: `flush()`, the fallback POST and `stop(true)` send it again, and it never goes over the socket. `flush()` now also POSTs while the socket is still connecting. `stop()` no longer reads the `WebSocket` global, which some runtimes do not define.
